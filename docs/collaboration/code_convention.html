Code Convention

Published

June 15, 2023

Modified

November 9, 2026

Reasoning

Code that follows established conventions is easier for others to read, whether they are collaborators, reviewers, or your future self several months later. Consistent code makes errors easier to find, replicated code easier to compare, and large changes possible without breaking the rest of the project.

I work mainly in the R programming language, so the rules below are R-specific. They combine the tidyverse style guide, the Google R style guide, and my own rules; where these disagree, the rules on this page win.

Style should be consistent within a project, so when you edit existing code, match the style around it.

Project setup

Project template

Every project is a self-contained unit with its data, code, and outputs. New projects start from my project template, which sets up the structure, packages, configuration, pipelines, and tests described here.

├─ Data/
│   ├─ Input/                   raw inputs
│   ├─ Processed/               processed data saved outside {targets}
│   ├─ Temp/                    disposable scratch files (git-ignored)
│   └─ Targets_data/            one {targets} store per pipeline (git-ignored)
├─ Outputs/
│   ├─ Data/
│   ├─ Figures/
│   └─ Tables/
├─ R/
│   ├─ ___Init_project___.R     restore or initialise the R environment
│   ├─ ___setup_project___.R    shared setup sourced by every script
│   ├─ Analyses/
│   │   ├─ 00_run_main.R        run all stages in order
│   │   ├─ 01_Data_preparation/ 00_run.R + pipeline.R
│   │   └─ 02_Main_analyses/    00_run.R + pipeline.R
│   ├─ Functions/               one function per file, grouped by area
│   └─ Tests/
│       ├─ Run_tests.R          full test suite
│       └─ testthat/            test-<function_name>.R
├─ renv/
├─ config.yml                   project configuration
├─ secrets_example.yaml         template for the machine-local secrets.yaml
├─ [project name].Rproj
└─ README.md

Reproducibility

  • Each R session is disposable. Every script must run from a fresh session with nothing in memory, so restart R often.
  • Save results that are expensive to compute to disk, either in a {targets} store or as an .rds file.
  • Build every path with {here}, never with a machine-specific absolute path. Large data stored outside the project are found through the data root set in the machine-local secrets.yaml.
  • Keep seeds, thresholds, figure sizes, and package lists in config.yml (read with {config}), never typed directly into scripts.
  • Manage packages with {renv}. Install with renv::install(), record the change with renv::snapshot(), and never edit renv.lock by hand.
  • Data/Temp/ is git-ignored and must not hold anything worth keeping.
  • Name outputs after the analysis that produced them, not after their current figure or table number in a manuscript, which changes during revision.

Folder and file names

  • Folders and data or output files use Capital_snake_style: Data/Input/, R/Functions/Data/, Outputs/Figures/.
  • Dates in file names are written as YYYY-MM-DD.
  • Function files and test files are named after their function, in lower snake case: prepare_survey_data.R, test-prepare_survey_data.R.
  • Number folders and scripts only when they form a fixed sequence of stages, such as 01_Data_preparation/ and 02_Main_analyses/.
  • Never put GitHub issue or pull-request numbers into file names, object names, target names, configuration values, or comments. The code must make sense without access to GitHub.

Stages and pipelines

The analysis runs as {targets} pipelines, one per stage. In each stage folder, pipeline.R declares the targets and 00_run.R runs them; R/Analyses/00_run_main.R runs all stages in order. Each pipeline keeps its results in its own store, which later stages can read from. Analysis variants, such as a different threshold or subset, are configuration profiles in config.yml, not copies of a pipeline. See Pipelines for how to write targets.

Scripts

One script, one task

A script does one task, which should be obvious from its name. It loads its own inputs, does its task, and saves its results. Order its sections as setup, inputs, transformations, outputs, and checks. Every script starts by sourcing the shared project setup:

library(here)

source(
  here::here("R/___setup_project___.R")
)

Script header

A script starts with a header holding the project name, the script name, the authors, and the year. A short description of what the script does may follow the header.

#----------------------------------------------------------#
#
#
#                     Project name
#
#                      Script name
#                      - continue
#
#                       Authors
#                        Year
#
#----------------------------------------------------------#
# Prepares the survey data for the main analyses.

Section headers

Each section starts with a capitalised name between two lines, followed by ----- so the editor lists it in the document outline. Leave an empty line before each header. There are three levels:

#----------------------------------------------------------#
# 1. Estimate diversity -----
#----------------------------------------------------------#


#--------------------------------------------------#
## 1.1. Fit model -----
#--------------------------------------------------#


#----------------------------------------#
### 1.1.1. Check convergence -----
#----------------------------------------#

Numbers are optional; when used, subsections are separated by ., and the first section, which sources the setup and loads the configuration, is 0. Setup:

#----------------------------------------------------------#
# 0. Setup -----
#----------------------------------------------------------#

Comments

  • Start a comment with a space after # and a capital letter.

  • Do not comment every line. Describe what a large or complex chunk does, and always explain why a non-standard approach was chosen.

  • A multi-line comment continues with an indented line:

    # This is a very long comment, where I need to describe
#    what this code is doing

  • An inline comment starts with a space after the code: n_iter = 100 # Enough for convergence.

  • Use only ASCII characters in R files, including comments; leave out diacritics and special symbols.

Line width

No line of R code is longer than 80 characters, including comments and roxygen2 documentation. Set a ruler at 80 characters in your editor. The limit does not apply to prose in Markdown or Quarto files.

Names

“There are only two hard things in Computer Science: cache invalidation and naming things.” (Phil Karlton)

Objects

Use lower snake_case and full, descriptive words for objects, arguments, functions, and columns. Do not use dots in names, as they clash with S3 method names. Objects are nouns and start with a prefix that says what type of object they are:

Prefix Use Example
data_ data frame or tibble data_diversity_survey
table_ summary or reporting table table_model_summary
list_ list list_diversity_per_plot
vec_ vector vec_region_names
mat_ matrix mat_species_cooccurrence
mod_ statistical model mod_diversity_linear
plot_ plot object plot_diversity_by_region
path_, file_, dir_ paths, file names, directories path_survey_data
config_ configuration object config_model
flag_ logical switch flag_rerun <- FALSE
sel_ the selected item, for example in a loop or from configuration sel_region
n_, seed_, formula_ counts, seeds, model formulas n_samples
res, res_ the object a function returns res_estimated_weight

A suffix can record the state of the data: _raw, _validated, _filtered, _prepared, _summary.

Do not overwrite transformed objects

Give each transformation a new name instead of overwriting the earlier object, so the meaning of a name does not depend on how far the script has run:

# Good
data_samples_filtered <-
  filter_samples(data_samples_raw)

data_samples_prepared <-
  prepare_samples(data_samples_filtered)

# Avoid
data_samples <-
  filter_samples(data_samples)

Functions

Function names are verbs and describe what the function returns or does. Choose the verb that matches what the function does:

Verb Use
load_ read an existing object from a file, URL, database, or target store
save_ write an object to disk
build_ construct a structured object from inputs in memory, without reading or writing files
prepare_ transform data into a form ready for analysis
validate_ check a requirement and stop with an error when it is not met
is_, has_ return TRUE or FALSE
resolve_ choose one value by a fixed rule or fallback
compute_ return a mathematical or algorithmic result
aggregate_ combine observations into grouped records
summarise_ reduce data to summary statistics or a table
fit_ fit a statistical or machine-learning model
predict_ generate predictions from a fitted model
evaluate_, score_ assess model performance or quality
diagnose_ return diagnostic checks of a model or data
select_ choose rows, variables, or a model by a fixed rule
plot_ return a plot object without saving it
run_ run a multi-step workflow with side effects
render_ produce a document or other rendered output

A precise domain verb, such as filter_, classify_, interpolate_, or normalise_, is fine when it is clearer. Avoid vague verbs such as get_ and make_, and vague variants such as _simple, _new, or _final. An internal helper may start with a single dot: .resolve_round_value().

Columns

Column names in data frames and tibbles also use snake_case; janitor::clean_names() converts them automatically. Interval columns are lwr_<coverage> and upr_<coverage>: lwr_95 is the 2.5th percentile and upr_95 the 97.5th. ## Layout

I prefer vertical code to horizontal code, so there are a lot of new lines. Indent with two spaces, never tabs, and do not use semicolons. Separate top-level statements with one empty line, but do not add empty lines inside a single expression (between arguments, pipe steps, or plot layers).

Assignment

Always assign with <-, never with -> or =. When the right-hand side is a function call or other expression, start it on a new line, indented by two spaces. Only a single literal value or NULL stays on the same line:

data_diversity <-
  load_survey_data(path = path_survey_data)

vec_regions <-
  c("Europe", "Asia", "Oceania")

n_iter <- 100L
flag_rerun <- FALSE

Function calls

Name the arguments, even when R would accept them by position. The exception is ..., whose arguments have no names. With two or more arguments, put each on its own line; a single argument stays on the line:

vec_selected_regions <-
  select_regions(data_regions = data_regions_raw)

data_diversity <-
  compute_diversity(
    data_community = data_community_prepared,
    method = "shannon"
  )

Function definitions

With two or more arguments, put each argument on its own line, indented by two spaces, and close with ) { on a separate line:

summarise_diversity <- function(
  data_diversity,
  group_var,
  min_n_samples = 1L
) {
  ...
}

A function with a single argument keeps it on the first line: prepare_survey_data <- function(data_raw) {.

Pipes

Use the native pipe |>, with a space before it and a new line after it. Use pipes instead of nested calls, so the code reads in the order it runs:

data_diversity_summary <-
  data_diversity |>
  dplyr::filter(n_samples > 10) |>
  dplyr::summarise(
    mean_diversity = mean(diversity),
    .by = region
  )

Use the {magrittr} pipe %>% only when the native pipe does not work cleanly, such as piping into a non-first argument with the . placeholder.

Control flow

The condition of if, for, and while always goes on its own indented line, followed by ) { on a separate line, even when the condition is short:

if (
  nrow(data_unmatched) > 0L
) {
  ...
} else {
  ...
}

for (
  sel_region in vec_regions
) {
  ...
}

Brackets and spaces

  • Put a space after a comma and around infix operators (==, +, -, <-, ~).
  • Do not put spaces around high-precedence operators: :, ::, $, @, [, [[, ^, and unary -.
  • Round brackets ( ) have no space before them in a function call.
  • Square brackets [ ] never have a space before them; leave a space for an empty index: data_cars[, 2].
  • Curly brackets { } are only for functions and expressions, never for grouping chunks of code. { is the last character on its line and } the first; keep } else { together.
  • Write TRUE and FALSE, never T and F.

Packages and the tidyverse

Namespaces

Write every call to a function from a package other than {base} with its namespace, so it is always clear where a function comes from. This includes {stats} and {utils}:

data_diversity |>
  dplyr::mutate(
    sd_diversity = stats::sd(diversity)
  )

Calls to {base} functions may be written with or without base::, except in tests, which namespace everything. Load packages once in the project setup, never with library() inside a function.

Prefer the tidyverse to base R

Base R Use instead
read.csv() readr::read_csv()
df$col dplyr::pull(df, col)
df$col <- ... dplyr::mutate(df, col = ...)
list$element purrr::chuck(list, "element")
lapply(), sapply(), mapply() purrr::map(), purrr::map_dbl(), purrr::map2()
grepl(), gsub() stringr::str_detect(), stringr::str_replace_all()
paste0(a, b) stringr::str_glue("{a}{b}")
paste(x, collapse = ", ") stringr::str_c(x, collapse = ", ")

Do not use:

  • $ to access columns or list elements;
  • paste() and paste0();
  • the apply() family;
  • attr() to attach information to an object (use a column, a list element, or a separate target instead);
  • eval(parse(...)) or get() inside data-masking functions;
  • superseded functions such as dplyr::transmute() and purrr::map_dfr().

{dplyr}

  • Join with dplyr::join_by(), and add multiple = "error" or unmatched = "error" when the data should guarantee a clean join.
  • After a grouped computation, dplyr::ungroup() the result or use .groups = "drop", unless the grouping is still needed.
  • Use dplyr::reframe() when a summary returns more than one row per group.

{purrr}

Pipe the input into purrr::map(), and name it first with rlang::set_names() to keep the names in the output. Write anonymous functions with the tilde (~), .x, and .y (or ..1, ..2 in purrr::pmap()), not with \(x). Use purrr::walk() when only the side effect matters, such as writing files, and bind results explicitly with purrr::list_rbind().

data_diversity_trends <-
  vec_regions |>
  rlang::set_names() |>
  purrr::map(
    .f = ~ compute_diversity_trend(
      data_diversity = data_diversity_prepared,
      sel_region = .x
    )
  ) |>
  purrr::list_rbind(names_to = "region")

When purrr::map() calls are nested, store the outer .x in a named object before the inner call, so the two are not confused.

Data masking

Inside a function, pass a column given as a bare name with {{ }}, and a column given as a string with .data[[col_name]]:

data_input |>
  dplyr::group_by({{ group_var }}) |>
  dplyr::summarise(
    mean_value = mean(.data[[value_col]]),
    .groups = "drop"
  )

Functions

Files and structure

  • Each function lives in its own file in R/Functions/<Area>/, named after the function. Group functions by what they do, not by which script uses them.
  • Extend an existing function rather than writing a near-copy of it.
  • A function does only what its name says: it does not source files, change global objects, call library(), or write files unless writing is its job.
  • Build the result first, name it res or res_*, and end with an explicit return(res).

Checks and messages

  • Check arguments with {assertthat}, always with a clear msg.
  • Raise problems found in the data during processing with cli::cli_abort(), and warnings or messages with cli::cli_warn() and cli::cli_inform() from {cli}. Do not use stop() or stopifnot().
  • A function that prints progress takes a verbose = TRUE argument and prints only when isTRUE(verbose). Errors are never silenced.

Documentation

Every function has {roxygen2} documentation directly above it, even outside a package, which also makes it easier to turn the functions into a package later. Each tag’s text starts on the next line. A complete function looks like this:

#' @title Summarise diversity per group
#' @description
#' Computes the mean diversity for each group with enough samples.
#' @param data_diversity
#' Data frame with a numeric column `diversity`.
#' @param group_var
#' Bare name of the grouping column.
#' @param min_n_samples
#' Minimum number of samples a group needs to be kept.
#' @param verbose
#' Logical. If `TRUE` (default), progress messages are printed.
#' @return
#' A tibble with one row per group and the column `mean_diversity`.
summarise_diversity <- function(
  data_diversity,
  group_var,
  min_n_samples = 1L,
  verbose = TRUE
) {
  assertthat::assert_that(
    is.data.frame(data_diversity),
    "diversity" %in% names(data_diversity),
    msg = "`data_diversity` must be a data frame with a `diversity` column."
  )

  if (
    isTRUE(verbose)
  ) {
    cli::cli_inform("Summarising diversity.")
  }

  res <-
    data_diversity |>
    dplyr::group_by({{ group_var }}) |>
    dplyr::filter(dplyr::n() >= min_n_samples) |>
    dplyr::summarise(
      mean_diversity = mean(diversity),
      .groups = "drop"
    )

  return(res)
}

Tests

  • Each function has its own {testthat} file, R/Tests/testthat/test-<function_name>.R.
  • Write the tests from the function’s documentation, before writing the function itself.
  • Test the intended behaviour, not whatever the code currently does: valid input, invalid input, the structure of the output, correct values on small hand-checked examples, and edge cases such as NA, empty input, or a single row.
  • Namespace every call in tests, including {base}: testthat::expect_equal(), base::nrow().
  • Expectations may be short one-line calls with positional arguments: testthat::expect_equal(base::nrow(res), 3L).
  • Use set.seed(900723) when a test involves randomness.
  • Test files have no script header and do not call library().
  • Run the full suite with Rscript R/Tests/Run_tests.R.

Pipelines

  • Target names are quoted strings and follow the object prefixes.
  • Above each target, write a short comment saying what it provides and why it is in the pipeline.
  • When the command is a single function call, write it directly, without { }. When it needs several steps, move them into a function in R/Functions/ and call that function, so the logic can be tested.
  • Information that would otherwise go into an attribute gets its own target.
  • Targets are used by later stages, so check what depends on a target before renaming or restructuring it.
list(
  # Raw survey data as delivered; every later target starts from it.
  targets::tar_target(
    name = "data_survey_raw",
    command = load_survey_data(path = path_survey_data)
  ),
  # Survey data with checked columns and units, used by all models.
  targets::tar_target(
    name = "data_survey_prepared",
    command = prepare_survey_data(data_raw = data_survey_raw)
  )
)

Figures

  • Read figure size, DPI, background, text sizes, and colour palettes from config.yml, once, in the setup section of the script. Never type them into figure code.
  • Wrap a non-trivial plot in a plot_ function that returns the plot, and save it in the script.
  • A colour stands for a scientific role and keeps that colour across all figures of a project. Do not rely on colour alone; add labels, line types, or ordering.
  • Add {ggplot2} layers in this order: data and aesthetics, facets, scales, labels, theme (ggplot2::theme_classic() as the base), canvas, then geoms from the bottom layer to the top.
  • Set the size with ggview::canvas() and save with ggview::save_ggplot() from {ggview}, so the saved file matches what you see.
plot_diversity_trend <-
  data_diversity |>
  ggplot2::ggplot(
    mapping = ggplot2::aes(
      x = age,
      y = diversity,
      colour = region
    )
  ) +
  ggplot2::facet_wrap(ggplot2::vars(region)) +
  ggplot2::scale_x_continuous(trans = "reverse") +
  ggplot2::labs(
    x = "Age (cal yr BP)",
    y = "Diversity",
    colour = "Region"
  ) +
  ggplot2::theme_classic() +
  ggview::canvas(
    width = graphical_options[["width"]],
    height = graphical_options[["height"]],
    units = graphical_options[["units"]],
    dpi = graphical_options[["dpi"]],
    bg = graphical_options[["bg"]]
  ) +
  ggplot2::geom_line() +
  ggplot2::geom_point(size = 0.8)

Teaching code

R code shown to students in my courses follows simpler rules, because students should be able to read it without knowing the tidyverse. It uses base R and base graphics, does not call library(), and writes pkg:: only for packages that R does not load by default. It keeps the object prefixes, the vertical layout, named arguments, and set.seed(900723). Code hidden from students, such as the code that prepares data sets and figures, follows the rules on this page.

Tools

{lintr} checks many of these rules as you type, and {styler} or Air format code automatically. They follow the tidyverse style guide, which differs from these rules in places, such as multi-line if conditions, so review what they change. The project template includes a .lintr file with an 80-character line limit and without the object-length and return-value linters. My editor setup is described in VS Code for R.

## Reasoning

Code that follows established conventions is easier for others to read, whether they are collaborators, reviewers, or your future self several months later.
Consistent code makes errors easier to find, replicated code easier to compare, and large changes possible without breaking the rest of the project.

I work mainly in the [R programming language](https://www.r-project.org/), so the rules below are R-specific.
They combine the [tidyverse style guide](https://style.tidyverse.org/), the [Google R style guide](https://google.github.io/styleguide/Rguide.html), and my own rules; where these disagree, the rules on this page win.

Style should be consistent within a project, so when you edit existing code, match the style around it.

  ```r
  # This is a very long comment, where I need to describe
  #    what this code is doing
  ```

- An inline comment starts with a space after the code: `n_iter = 100 # Enough for convergence`.
- Use only ASCII characters in R files, including comments; leave out diacritics and special symbols.

### Line width

No line of R code is longer than 80 characters, including comments and roxygen2 documentation.
Set a ruler at 80 characters in your editor.
The limit does not apply to prose in Markdown or Quarto files.

## Names

> "There are only two hard things in Computer Science: cache invalidation and naming things." (Phil Karlton)

### Objects

Use lower `snake_case` and full, descriptive words for objects, arguments, functions, and columns.
Do not use dots in names, as they clash with S3 method names.
Objects are nouns and start with a prefix that says what type of object they are:

| Prefix | Use | Example |
| --- | --- | --- |
| `data_` | data frame or tibble | `data_diversity_survey` |
| `table_` | summary or reporting table | `table_model_summary` |
| `list_` | list | `list_diversity_per_plot` |
| `vec_` | vector | `vec_region_names` |
| `mat_` | matrix | `mat_species_cooccurrence` |
| `mod_` | statistical model | `mod_diversity_linear` |
| `plot_` | plot object | `plot_diversity_by_region` |
| `path_`, `file_`, `dir_` | paths, file names, directories | `path_survey_data` |
| `config_` | configuration object | `config_model` |
| `flag_` | logical switch | `flag_rerun <- FALSE` |
| `sel_` | the selected item, for example in a loop or from configuration | `sel_region` |
| `n_`, `seed_`, `formula_` | counts, seeds, model formulas | `n_samples` |
| `res`, `res_` | the object a function returns | `res_estimated_weight` |

A suffix can record the state of the data: `_raw`, `_validated`, `_filtered`, `_prepared`, `_summary`.

### Do not overwrite transformed objects

Give each transformation a new name instead of overwriting the earlier object, so the meaning of a name does not depend on how far the script has run:

```r
# Good
data_samples_filtered <-
  filter_samples(data_samples_raw)

data_samples_prepared <-
  prepare_samples(data_samples_filtered)

# Avoid
data_samples <-
  filter_samples(data_samples)
```

### Functions

Function names are verbs and describe what the function returns or does.
Choose the verb that matches what the function does:

| Verb | Use |
| --- | --- |
| `load_` | read an existing object from a file, URL, database, or target store |
| `save_` | write an object to disk |
| `build_` | construct a structured object from inputs in memory, without reading or writing files |
| `prepare_` | transform data into a form ready for analysis |
| `validate_` | check a requirement and stop with an error when it is not met |
| `is_`, `has_` | return `TRUE` or `FALSE` |
| `resolve_` | choose one value by a fixed rule or fallback |
| `compute_` | return a mathematical or algorithmic result |
| `aggregate_` | combine observations into grouped records |
| `summarise_` | reduce data to summary statistics or a table |
| `fit_` | fit a statistical or machine-learning model |
| `predict_` | generate predictions from a fitted model |
| `evaluate_`, `score_` | assess model performance or quality |
| `diagnose_` | return diagnostic checks of a model or data |
| `select_` | choose rows, variables, or a model by a fixed rule |
| `plot_` | return a plot object without saving it |
| `run_` | run a multi-step workflow with side effects |
| `render_` | produce a document or other rendered output |

A precise domain verb, such as `filter_`, `classify_`, `interpolate_`, or `normalise_`, is fine when it is clearer.
Avoid vague verbs such as `get_` and `make_`, and vague variants such as `_simple`, `_new`, or `_final`.
An internal helper may start with a single dot: `.resolve_round_value()`.

### Columns

Column names in data frames and tibbles also use `snake_case`; [janitor::clean_names()](https://sfirke.github.io/janitor/) converts them automatically.
Interval columns are `lwr_<coverage>` and `upr_<coverage>`: `lwr_95` is the 2.5th percentile and `upr_95` the 97.5th.
## Layout

I prefer vertical code to horizontal code, so there are a lot of new lines.
Indent with two spaces, never tabs, and do not use semicolons.
Separate top-level statements with one empty line, but do not add empty lines inside a single expression (between arguments, pipe steps, or plot layers).

### Assignment

Always assign with `<-`, never with `->` or `=`.
When the right-hand side is a function call or other expression, start it on a new line, indented by two spaces.
Only a single literal value or `NULL` stays on the same line:

```r
data_diversity <-
  load_survey_data(path = path_survey_data)

vec_regions <-
  c("Europe", "Asia", "Oceania")

n_iter <- 100L
flag_rerun <- FALSE
```

### Function calls

Name the arguments, even when R would accept them by position.
The exception is `...`, whose arguments have no names.
With two or more arguments, put each on its own line; a single argument stays on the line:

```r
vec_selected_regions <-
  select_regions(data_regions = data_regions_raw)

data_diversity <-
  compute_diversity(
    data_community = data_community_prepared,
    method = "shannon"
  )
```

### Function definitions

With two or more arguments, put each argument on its own line, indented by two spaces, and close with `) {` on a separate line:

```r
summarise_diversity <- function(
  data_diversity,
  group_var,
  min_n_samples = 1L
) {
  ...
}
```

A function with a single argument keeps it on the first line: `prepare_survey_data <- function(data_raw) {`.

### Pipes

Use the native pipe `|>`, with a space before it and a new line after it.
Use pipes instead of nested calls, so the code reads in the order it runs:

```r
data_diversity_summary <-
  data_diversity |>
  dplyr::filter(n_samples > 10) |>
  dplyr::summarise(
    mean_diversity = mean(diversity),
    .by = region
  )
```

Use the {magrittr} pipe `%>%` only when the native pipe does not work cleanly, such as piping into a non-first argument with the `.` placeholder.

### Control flow

The condition of `if`, `for`, and `while` always goes on its own indented line, followed by `) {` on a separate line, even when the condition is short:

```r
if (
  nrow(data_unmatched) > 0L
) {
  ...
} else {
  ...
}

for (
  sel_region in vec_regions
) {
  ...
}
```

### Brackets and spaces

- Put a space after a comma and around infix operators (`==`, `+`, `-`, `<-`, `~`).
- Do not put spaces around high-precedence operators: `:`, `::`, `$`, `@`, `[`, `[[`, `^`, and unary `-`.
- Round brackets `( )` have no space before them in a function call.
- Square brackets `[ ]` never have a space before them; leave a space for an empty index: `data_cars[, 2]`.
- Curly brackets `{ }` are only for functions and expressions, never for grouping chunks of code. `{` is the last character on its line and `}` the first; keep `} else {` together.
- Write `TRUE` and `FALSE`, never `T` and `F`.

## Packages and the tidyverse

### Namespaces

Write every call to a function from a package other than {base} with its namespace, so it is always clear where a function comes from.
This includes {stats} and {utils}:

```r
data_diversity |>
  dplyr::mutate(
    sd_diversity = stats::sd(diversity)
  )
```

Calls to {base} functions may be written with or without `base::`, except in tests, which namespace everything.
Load packages once in the project setup, never with `library()` inside a function.

### Prefer the tidyverse to base R

| Base R | Use instead |
| --- | --- |
| `read.csv()` | `readr::read_csv()` |
| `df$col` | `dplyr::pull(df, col)` |
| `df$col <- ...` | `dplyr::mutate(df, col = ...)` |
| `list$element` | `purrr::chuck(list, "element")` |
| `lapply()`, `sapply()`, `mapply()` | `purrr::map()`, `purrr::map_dbl()`, `purrr::map2()` |
| `grepl()`, `gsub()` | `stringr::str_detect()`, `stringr::str_replace_all()` |
| `paste0(a, b)` | `stringr::str_glue("{a}{b}")` |
| `paste(x, collapse = ", ")` | `stringr::str_c(x, collapse = ", ")` |

Do not use:

- `$` to access columns or list elements;
- `paste()` and `paste0()`;
- the `apply()` family;
- `attr()` to attach information to an object (use a column, a list element, or a separate target instead);
- `eval(parse(...))` or `get()` inside data-masking functions;
- superseded functions such as `dplyr::transmute()` and `purrr::map_dfr()`.

### {dplyr}

- Join with `dplyr::join_by()`, and add `multiple = "error"` or `unmatched = "error"` when the data should guarantee a clean join.
- After a grouped computation, `dplyr::ungroup()` the result or use `.groups = "drop"`, unless the grouping is still needed.
- Use `dplyr::reframe()` when a summary returns more than one row per group.

### {purrr}

Pipe the input into `purrr::map()`, and name it first with `rlang::set_names()` to keep the names in the output.
Write anonymous functions with the tilde (`~`), `.x`, and `.y` (or `..1`, `..2` in `purrr::pmap()`), not with `\(x)`.
Use `purrr::walk()` when only the side effect matters, such as writing files, and bind results explicitly with `purrr::list_rbind()`.

```r
data_diversity_trends <-
  vec_regions |>
  rlang::set_names() |>
  purrr::map(
    .f = ~ compute_diversity_trend(
      data_diversity = data_diversity_prepared,
      sel_region = .x
    )
  ) |>
  purrr::list_rbind(names_to = "region")
```

When `purrr::map()` calls are nested, store the outer `.x` in a named object before the inner call, so the two are not confused.

### Data masking

Inside a function, pass a column given as a bare name with `{{ }}`, and a column given as a string with `.data[[col_name]]`:

```r
data_input |>
  dplyr::group_by({{ group_var }}) |>
  dplyr::summarise(
    mean_value = mean(.data[[value_col]]),
    .groups = "drop"
  )
```

## Functions

### Files and structure

- Each function lives in its own file in `R/Functions/<Area>/`, named after the function. Group functions by what they do, not by which script uses them.
- Extend an existing function rather than writing a near-copy of it.
- A function does only what its name says: it does not source files, change global objects, call `library()`, or write files unless writing is its job.
- Build the result first, name it `res` or `res_*`, and end with an explicit `return(res)`.

### Checks and messages

- Check arguments with [{assertthat}](https://github.com/hadley/assertthat), always with a clear `msg`.
- Raise problems found in the data during processing with `cli::cli_abort()`, and warnings or messages with `cli::cli_warn()` and `cli::cli_inform()` from [{cli}](https://cli.r-lib.org/). Do not use `stop()` or `stopifnot()`.
- A function that prints progress takes a `verbose = TRUE` argument and prints only when `isTRUE(verbose)`. Errors are never silenced.

### Documentation

Every function has [{roxygen2}](https://roxygen2.r-lib.org/) documentation directly above it, even outside a package, which also makes it easier to turn the functions into a package later.
Each tag's text starts on the next line.
A complete function looks like this:

```r
#' @title Summarise diversity per group
#' @description
#' Computes the mean diversity for each group with enough samples.
#' @param data_diversity
#' Data frame with a numeric column `diversity`.
#' @param group_var
#' Bare name of the grouping column.
#' @param min_n_samples
#' Minimum number of samples a group needs to be kept.
#' @param verbose
#' Logical. If `TRUE` (default), progress messages are printed.
#' @return
#' A tibble with one row per group and the column `mean_diversity`.
summarise_diversity <- function(
  data_diversity,
  group_var,
  min_n_samples = 1L,
  verbose = TRUE
) {
  assertthat::assert_that(
    is.data.frame(data_diversity),
    "diversity" %in% names(data_diversity),
    msg = "`data_diversity` must be a data frame with a `diversity` column."
  )

  if (
    isTRUE(verbose)
  ) {
    cli::cli_inform("Summarising diversity.")
  }

  res <-
    data_diversity |>
    dplyr::group_by({{ group_var }}) |>
    dplyr::filter(dplyr::n() >= min_n_samples) |>
    dplyr::summarise(
      mean_diversity = mean(diversity),
      .groups = "drop"
    )

  return(res)
}
```

## Tests

- Each function has its own [{testthat}](https://testthat.r-lib.org/) file, `R/Tests/testthat/test-<function_name>.R`.
- Write the tests from the function's documentation, before writing the function itself.
- Test the intended behaviour, not whatever the code currently does: valid input, invalid input, the structure of the output, correct values on small hand-checked examples, and edge cases such as `NA`, empty input, or a single row.
- Namespace every call in tests, including {base}: `testthat::expect_equal()`, `base::nrow()`.
- Expectations may be short one-line calls with positional arguments: `testthat::expect_equal(base::nrow(res), 3L)`.
- Use `set.seed(900723)` when a test involves randomness.
- Test files have no script header and do not call `library()`.
- Run the full suite with `Rscript R/Tests/Run_tests.R`.

## Pipelines {#pipelines}

- Target names are quoted strings and follow the object [prefixes](#objects).
- Above each target, write a short comment saying what it provides and why it is in the pipeline.
- When the command is a single function call, write it directly, without `{ }`. When it needs several steps, move them into a function in `R/Functions/` and call that function, so the logic can be tested.
- Information that would otherwise go into an attribute gets its own target.
- Targets are used by later stages, so check what depends on a target before renaming or restructuring it.

```r
list(
  # Raw survey data as delivered; every later target starts from it.
  targets::tar_target(
    name = "data_survey_raw",
    command = load_survey_data(path = path_survey_data)
  ),
  # Survey data with checked columns and units, used by all models.
  targets::tar_target(
    name = "data_survey_prepared",
    command = prepare_survey_data(data_raw = data_survey_raw)
  )
)
```

## Figures

- Read figure size, DPI, background, text sizes, and colour palettes from `config.yml`, once, in the setup section of the script. Never type them into figure code.
- Wrap a non-trivial plot in a `plot_` function that returns the plot, and save it in the script.
- A colour stands for a scientific role and keeps that colour across all figures of a project. Do not rely on colour alone; add labels, line types, or ordering.
- Add {ggplot2} layers in this order: data and aesthetics, facets, scales, labels, theme (`ggplot2::theme_classic()` as the base), canvas, then geoms from the bottom layer to the top.
- Set the size with `ggview::canvas()` and save with `ggview::save_ggplot()` from [{ggview}](https://github.com/idmn/ggview), so the saved file matches what you see.

```r
plot_diversity_trend <-
  data_diversity |>
  ggplot2::ggplot(
    mapping = ggplot2::aes(
      x = age,
      y = diversity,
      colour = region
    )
  ) +
  ggplot2::facet_wrap(ggplot2::vars(region)) +
  ggplot2::scale_x_continuous(trans = "reverse") +
  ggplot2::labs(
    x = "Age (cal yr BP)",
    y = "Diversity",
    colour = "Region"
  ) +
  ggplot2::theme_classic() +
  ggview::canvas(
    width = graphical_options[["width"]],
    height = graphical_options[["height"]],
    units = graphical_options[["units"]],
    dpi = graphical_options[["dpi"]],
    bg = graphical_options[["bg"]]
  ) +
  ggplot2::geom_line() +
  ggplot2::geom_point(size = 0.8)
```

## Teaching code

R code shown to students in my courses follows simpler rules, because students should be able to read it without knowing the tidyverse.
It uses base R and base graphics, does not call `library()`, and writes `pkg::` only for packages that R does not load by default.
It keeps the object prefixes, the vertical layout, named arguments, and `set.seed(900723)`.
Code hidden from students, such as the code that prepares data sets and figures, follows the rules on this page.
